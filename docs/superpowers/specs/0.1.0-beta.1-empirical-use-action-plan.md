# Memoria 0.1.0-beta.1 - Empirical Use Data Action Plan

Date: 2026-07-17
Status: action plan, **v3** — supersedes the 2026-07-10 v2. Reconciled
with the beta.1 design wave (I1/O1/O2/R2/V2/U1/U2 specs and plans, all
merged 2026-07-16/17); every mechanism this plan names now has a designed
owner with exact ids, and Phases 0–3 are written as runnable protocols
(issue #1506). v2's contradictions repaired: the steering-before-import
step is now *frame the project* (steering derives from active projects,
O1 spec §4); fixture preregistration points at the R2 form; the diary
template, stop rules, and decision-rule registry cite their product
mechanisms instead of describing intentions.

## 1. Requirements (unchanged in substance)

The beta.1 blockers need empirical data for product decisions, not a
large analytics system. The plan must:

- answer only the blocker and validation questions in the beta.1
  requirements and design docs, plus the dossier's open questions
  decidable by observation;
- collect enough repeated real-use evidence to make a decision;
- avoid raw content logging unless a user explicitly saves an artifact;
- preserve the single-user local-first posture;
- produce decisions that update the beta.1 ledger
  (`0.1.0-beta.1-decisions.md`), the beta.1 design, or the dossier
  roadmap — never raw notes promoted as conclusions.

Two constraints remain hard: **disposition telemetry is
non-backfillable** — instrumentation precedes all ingestion, which is now
a plan-level gate (the O2 plan may not execute until the I1 plan is
implemented and merged); and **the seeded-error verdict is the license
for real use** — no dogfood session on the real vault until the battery
passes.

## 2. Instrumentation (designed; lands with the I1 plan)

The shared event shape shipped with the alpha.21 skeleton, and the field
table below matches `engine/empirical_events.py` as shipped. The I1
full-wiring plan (`2026-07-16-i1-full-wiring.md`) delivers the rest
before any ingestion: the non-chained `telemetry_events` plane (v19),
the six disposition call-sites under the `proposal_ref` provenance
principle, the first `read-observed.v1` emitters, the attention
ordering/flow instrumentation, the raw-counts dashboard, and the seeded
decision-rule registry. O1 adds `onboarding-step`; O2 adds
`import-run.v1`. The v2 rule "do not build a dashboard before the events
exist" is honored *inside* the I1 plan's own ordering (events land in
its T section, the dashboard in its H section).

| Field | Purpose |
| --- | --- |
| `timestamp` | ordering and session reconstruction |
| `session_id` | one reading/writing/SRD work session (client events only; server rows carry NULL and metrics bucket by UTC day) |
| `project_id` | compare repeated loops inside one project |
| `surface` | CLI, HTTP, MCP, editor, manual |
| `workflow` | ask, gap, evidence-review, canvas, draft, SRD, export, import, attention |
| `item_type` / `item_id` | reviewed object without storing body text |
| `variant` | table/canvas, BM25/FTS/vector/hybrid, human/null/assisted |
| `decision` | accept, reject, edit, defer, override, abandon |
| `duration_s` | PI load and return-to-work cost |
| `outcome` | kept artifact, fallback, exported, blocked |
| `reason_code` | short controlled reason; free text optional and local |
| `loudness` | quiet, notice, alert, block — attention routing observed |
| `staleness_hit` | read served stale/demoted state before a scan caught up |

## 3. Data Collection Phases — runnable protocols

Roles throughout: **the PI** makes judgments, writes the five-line diary,
and runs the sessions; **the agent** automates setup, collects the
measurements, and summarizes evidence at review time. Observations land
in exactly four places: the telemetry table (automatic), the journal
(dispositions, automatic), the session diary (PI), and the decision-rule
registry + beta.1 ledger (review outcomes).

### Phase 0 - License, Baseline, Fixtures (1-2 sessions)

1. **Battery**: `memoria eval seeded-error-verdict --workspace
   test-vault/vault --json` — verdict must be green. *No real-vault work
   until it passes.* (Agent runs; PI reads the verdict.)
2. **Disposition flow proof**: one synthetic capture → triage →
   `memoria attention resolve --apply` → one `disposition.v1` journal
   row visible (the I1 acceptance criterion, re-run as a session check).
3. **Null workflow**: the PI records one small project through the
   existing Zotero/Obsidian/ChatGPT path — diary entries only; this is
   the comparison baseline for "helped".
4. **Retrieval fixture preregistration**: the R2 form is the mechanism —
   cases in `tests/fixtures/retrieval/*.yaml` (`{id, shape, query, gold,
   metric, registered, frozen}`); register Shape-1/Shape-2 cases over the
   seed corpus **before** any default-promotion claim; freezing happens
   before the R3 spike, and the loader refuses unfrozen fixtures in
   spike mode.
5. **Seed corpus**: decided and recorded — the licensing rule is a dated
   ledger entry (2026-07-16) and the eight verified sources ship as the
   O1 manifest. Nothing to select in-phase; `memoria seed install` is
   the runway.
6. **Diary**: the template is seeded at
   `system/templates/session-diary.md` (goal / workflow used / artifact
   kept / blocker hit / fallback used). Copy per session; local raw
   material, deleted or archived after decisions are recorded (§6).

Exit: verdict green, disposition row proven, baseline recorded, fixture
cases registered. No product decision yet.

### Phase 1 - Instrumented Staged Onboarding (10 → 100; 1000 is beta.2)

**Frame the project before the first import** — steering derives from
active projects (O1 spec §4: effective steering = active projects +
hubs + question notes + Watch-for, minus Muted); prune Watch-for/Muted
in `steering.md` if the frame needs supplementing. (This replaces v2's
"write steering.md before the first import".)

Run the O2 staged protocol (the staged-run block in the O2 plan,
consuming LOOP.13's amended acceptance): stage 1 = 10 works, stage 2 =
100 works, one `memoria work import --enrich` bulk call per stage over a
real Zotero BibTeX export.

Measured per stage, each with its mechanism:

- import wall-clock and index rebuild → `import-run.v1`
  (`duration_s`, `index_refresh_s`);
- duplicate-triage counts → `import-run.v1` (`duplicates_flagged`) + the
  run's worklist;
- retraction counts → **a queue-drain measurement**: run `memoria
  workspace run` after each stage (the same drain the enrichment-load
  metric needs) and count the `source-retraction` flags the queued
  `enrich-source` jobs raise on execution, plus the standing sweep's own
  alerts. `--enrich` only *queues* those jobs, so retraction truth does
  not exist when the import command returns and `import-run.v1` carries
  no retraction field — the drain is the moment the count becomes real
  ([#1517](https://github.com/eranroseman/memoria-vault/issues/1517),
  2026-08-01);
- attention items minted per 100 works, and whether triage stays inside
  a bounded ~60-minute batch → the flow panel (`attention-admitted`) and
  the run worklist as the batch artifact;
- enrichment provider load → enrichment result payloads under
  `--enrich`, read after `memoria workspace run` drains the stage's
  queued jobs;
- Shape-1/Shape-2 query latency → the protocol script times `memoria
  ask` and `memoria explore` (>200 ms interactive at any stage triggers
  the substrate re-comparison early — the R2 watch);
- journal/DB growth → protocol script sizing.

**Stop rule (pre-registered as the `staged-import` registry entry):**
after each stage, if the triage worklist did not fit one session or
rebuild/query latency broke the session's flow, stop and record — the
observation IS the finding.

Exit: 100-work catalog admitted or a recorded stop; per-stage metrics
logged; first gap run executed against the full library.

### Phase 2 - Guided Dogfood Loops (two full loops or ten sessions)

Two candidate projects, at least one required: (a) a real research
inquiry; (b) **Memoria-inside-Memoria** — the product's own design
questions as a project.

The session frame is the U2 cockpit: open with the deep screen
(`memoria cockpit --project <p>`), triage with `--triage`, review with
`memoria review`, close with the diary. Run each project through:
source/capture/digest → note/claim extraction → gap analysis
(`memoria project gaps`) → project slice → canvas/table comparison →
outline/draft → SRD → evidence review → export attempt → capture the
deliverable back into the catalog.

Automatic capture (no PI burden): dispositions per gate item
(`disposition.v1` from resolve/review/curate calls), `staleness_hit`
per read (`read-observed.v1`), attention flow, review telemetry
(items/session, time/item, reopens — V2's pre-registered set). Diary
capture (PI): the five lines, plus fallbacks to the null workflow with
why, fulltext-consultation events (opened PDF vs extracted text vs
needed an anchored span), and outline-composition friction (list
reorder sufficed vs reached for spatial arrangement — the
canvas-as-authoring trigger observation).

Exit: every blocker has at least one real event trail, or is explicitly
still unobservable because its mechanism does not exist.

### Phase 3 - Decision Review (one session)

For each blocker: **keep / simplify / defer / instrument more.** The
decision-rule registry is the working ledger: the agent assembles the
evidence per rule (dashboard values, telemetry queries, diary quotes);
the PI decides; fired/retired statuses flip in
`.memoria/config/decision-rules.yaml`; durable decisions land as dated
Y-statements in `0.1.0-beta.1-decisions.md`. Dossier items decidable
here: fulltext v2 shape, warrant brainstorm scheduling,
reactive-substrate priority, embedded-panel earn-back.

### Phase 4 - Validation Runs

After the relevant mechanism exists, run design §8.2 protocols: PI
review load; complementarity and payoff; canvas threshold; draft
write-back residual; exploration value; retrieval default activation
(against the **frozen** fixture set only); LLM call-site regression;
provider conflicts and topic ownership. Exit: each protocol has a
pass/defer/simplify decision and the evidence path.

## 4. Blocker Data Plan

The table below is **seeded verbatim as the decision-rule registry**
(I1 plan H.3: fifteen rows + `attention-throttle`; O2 adds
`staged-import` — seventeen armed rules). Registry ids in parentheses;
`auto` rules are dashboard-evaluated, the rest are diary-fed reminders.

| Blocker (registry id) | Data to collect | Minimum observation | Decision rule |
| --- | --- | --- | --- |
| SRD contract (`srd-contract`) | sections added/edited/deleted, unresolved requirements, missing trace links | two SRDs or one revised twice | Keep sections that survive real editing; rare ones to optional appendix |
| Evidence-review UI (`evidence-review-sizing`, auto) | items/session, time/item, accept/reject/edit/defer, reopen rate | ten items across two sessions | Batch and filter until review fits a session; if skipped, simplify the gate |
| Seed corpus (`seed-corpus`) | source list, license, fetch method, time to first grounded answer | one clean install rehearsal | Ship only clear-license sources with first answer under 30 minutes (measured by `onboarding-step`: `first-answer.ts − init-done.ts`) |
| Workspace/gate topology (`workspace-gate-topology`) | path between ask/review/writing/SRD/export; context switches; abandons | two full loops | Shortest path avoiding lost-return or hidden-gate failures |
| Export target (`export-target`) | recipient/tool, format, refusal reasons, cleanup time | two export attempts | First target appearing in real use (markdown + bibliography is the acceptance-tested baseline, V2 §5); defer live citation fields unless required |
| Multi-device topology (`multi-device-topology`) | second-device attempts, conflicts, sync workarounds | all sessions | Single-writer unless repeated real handoffs demand more |
| Raw dataset bundling (`raw-dataset-bundling`) | dataset size/type, mutation, sharing/export need | every dataset project | Catalog-by-reference unless a real export requires packaged data |
| `mode: work` creation (`mode-work-creation`) | creation attempts, confusion, alias requests | all Work-note creations | Alias only if reached for or worked around repeatedly |
| Non-API schema drift (`non-api-schema-drift`) | drift incidents, stale doc fields, failed checks | every release-doc/schema edit | Cheapest lint that catches observed drift (the doc-claims gate is the shipped floor) |
| Fulltext v2 shape (`fulltext-v2-shape`) | PDF-opens vs extracted-text reads vs anchored-span requests | every source consultation in Phase 2 | If spans are consumed via engine and reading happens in PDF, full v2; if file reads persist, partial retirement |
| Warrant touch budget (`warrant-touch-budget`) | under-warranted findings raised, "state the warrant" demands, PI minutes per explicit warrant | one full project loop | If explicit warrants stay under budget and get demanded, ratify hybrid-with-nodes; if never demanded, keep demandable-only and defer nodes (`edge-write.v1` counts are the input) |
| Reactive-substrate priority (`reactive-substrate-priority`, auto) | `staleness_hit` count, index-refresh latency, on-read wait | all sessions | Frequent staleness or painful refresh promotes the daemon; silence defers it |
| Two-window friction (`two-window-friction`) | context switches between editor and agent per session, dropped handoffs, context-read misses | all Phase 2 sessions | Repeated friction triggers the embedded-panel earn-back; otherwise plugin+agent stands (the cockpit's context-handoff block is the measured artifact) |
| Canvas authoring (`canvas-authoring`) | outline-composition friction events | every outline session in Phase 2 | Repeated spatial reaching admits canvas-as-authoring; silence keeps canvases projection-only |
| Attention loudness (`attention-loudness`, auto) | items per loudness level, triage deferrals | all sessions | Calibrate the loudness policy; any routine alert means a mis-tiered producer |
| — (`attention-throttle`, auto) | attention inflow vs drain per UTC day | rolling seven-day window | Recommend quieting or pausing the top producer |
| — (`staged-import`) | triage-fit and felt latency per import stage | each stage (10, then 100) | Stop the protocol and record — the observation IS the finding |

## 5. Validation Metric Plan (mechanisms named)

| Protocol | Primary measure | Guardrail |
| --- | --- | --- |
| PI review load | reviewed items/session and time/item (review telemetry) | no hidden auto-approval |
| Complementarity | assisted vs null workflow outcome | review cost included |
| Payoff | kept artifacts and fallback rate | no synthetic health score (the dashboard is raw counts by contract) |
| Canvas threshold | canvas edits/use vs table use | table remains available |
| Draft write-back | promoted notes kept/rejected/reworked | no auto-write to graph |
| Exploration | acted-on exploration candidates (dashboard panel 6) | no relevance stream pollution |
| Retrieval default | preregistered recall/grounding/latency/cost on the frozen set | BM25 default until beaten |
| LLM call-site | eval pass/fail against baseline | shadow-first promotion only |
| Provider/topic quality | conflict rate and PI corrections | conflicts stay visible |
| Onboarding ergonomics | triage minutes per 100 admitted works; the five `onboarding-step` deltas | bounded batches; near-empty queues recover post-import |

## 6. Operating Cadence

- Log events during the session (automatic); write the diary immediately
  after (PI).
- `memoria dashboard` opens the weekly review pass (the trend-informed
  ritual, I1 §6.5); review blocker evidence weekly or after five
  sessions.
- Promote only decisions, not raw telemetry, into the ledger or the
  dossier roadmap.
- Delete or archive local raw diary notes after the decision is
  recorded.

## 7. What Not To Build Yet

- No dashboard panels beyond I1's seven raw-count panels; no composite
  scores ever.
- No custom survey system; no broad user study before the self-use loop
  works.
- No retrieval default switch before the frozen preregistered fixtures
  beat BM25.
- No daemon (Tier A) before `staleness_hit` data justifies its
  priority — the read barrier keeps correctness meanwhile.
- No warrant-node schema work before the touch-budget observation
  (`edge-write.v1` counts).
- No code-execution data collection for beta.1; SRD is the code-side
  output.
